# trust/distrusted-root

**Certificate is, or chains to, emSign ECC Root CA - G3, a root removed from browser trust stores.**
Severity: high.

Reported by `cryptoserve scan` and `cryptoserve gate` with the id `trust/distrusted-root`, and by the
certificate engine as an error (so `valid` is false) wherever a certificate is verified:
`POST /api/v1/certificates/verify`, `POST /api/v1/certificates/verify-chain`, `cryptoserve certs verify`
and the Verify tab of the dashboard's Certificates page.

## What was found

After the eMudhra intermediate key compromise (Mozilla Bug 2083449), Mozilla removed this root
from its root store on 2026-10-20, and Chrome's removal date for all devices is 2026-10-27. A client stops
trusting chains that end at this root once its copy of Mozilla's or Chrome's root store drops the root.

Two rules raise this finding, and both match on the key, never on a name:

| Rule | The certificate | Value shown | `valueType` |
|---|---|---|---|
| 3 | is the root itself, for example inside a CA bundle or trust store committed to the repository. | the certificate's SPKI SHA-256 | `spkiSha256` |
| 4 | has a signature that verifies under the root's key: the root's key signed it directly, whether or not the root is in the same file. | the certificate's own SHA-256, with the root's key in `issuerSpkiSha256` | `certSha256` |

In the certificate engine the last certificate of a chain is its anchor: rule 3 applies when it is the root,
and rule 4 when the root was not supplied. A certificate from another eMudhra root, emSign Root CA - G1 for
example, is not flagged. `cryptoserve scan` reads only the files in the scanned tree, and a verify sees only the
certificates it is given. A result with no finding is not an all-clear: the check compared only those
certificates with the listed keys, and did not check the chain behind any certificate's issuer.

## Verify

Run from the directory you scanned. `FILE` is the finding's file and `LINE` the line of the certificate's
`-----BEGIN CERTIFICATE-----` header; both are in the finding. The scan prints each command ready to run, and
uses the shorter `openssl x509 -in FILE` form when the certificate is the first PEM block of its file.

Rule 3 prints the finding's `matchedValue`:

```sh
awk 'NR>=LINE' FILE | openssl x509 -noout -pubkey | openssl pkey -pubin -outform DER | openssl dgst -sha256 -binary | od -An -tx1 | tr -d ' \n'
```

Rule 4 prints the finding's `matchedValue`, the certificate's own SHA-256:

```sh
awk 'NR>=LINE' FILE | openssl x509 -outform DER | openssl dgst -sha256 -binary | od -An -tx1 | tr -d ' \n'
```

The commands use only openssl and POSIX tools and read nothing from the network.
Checked under OpenSSL 4.0.3 and LibreSSL 3.3.6, they print the same bytes.

To confirm a rule 4 signature, copy the certificate to its own file (`cert.pem`) and take the root from this
repository, `testdata/trust-keys/root/emsign-ecc-root-ca-g3.pem`. Then:

```sh
openssl verify -no_check_time -partial_chain -trusted emsign-ecc-root-ca-g3.pem cert.pem
```

prints `cert.pem: OK`. This needs an openssl that accepts `-partial_chain` and `-no_check_time`: OpenSSL
4.0.3 does; LibreSSL 3.3.6 does not.

## Fix

> Move the chain to a CA whose root stays trusted, and remove emSign ECC Root CA - G3 from any bundle you ship; Chrome's removal date for all devices is 2026-10-27.

For a trust store or CA bundle you ship (rule 3): remove emSign ECC Root CA - G3 from it, and keep revocation
checking on, or block the six listed TLS keys by SPKI hash, because the cross-signed copies of the listed
intermediates chain to a different root that some trust stores keep.
A file that lists distrusted certificates on purpose needs no change.
