# trust/compromised-ca-key

**Certificate uses, or is signed by, a publicly compromised CA key.** Severity: critical.

Reported by `cryptoserve scan` and `cryptoserve gate` with the id `trust/compromised-ca-key`, and by the
certificate engine as an error (so `valid` is false) wherever a certificate is verified:
`POST /api/v1/certificates/verify`, `POST /api/v1/certificates/verify-chain`, `cryptoserve certs verify`
and the Verify tab of the dashboard's Certificates page.

## What was found

The certificate's public key, or the key that signed it, is one of the eight eMudhra intermediate CA keys
listed below: six for TLS (EM DV, OV and EV TLS CA - G3B and - G3C) and two for code signing (EM OV CS CA - G3B
and - G3C). Their private keys were recovered independently by several parties, Mozilla among them, after a
report to the root programs and to eMudhra on 2026-10-17 (Mozilla Bug 2083449, comments 0 and 18). eMudhra
revoked its eight certificates on 2026-10-18, the cross-signed copies were revoked on 2026-10-19, and
Chrome and Firefox block the six TLS keys. The keys are compromised now, without a quantum computer: anyone
holding a listed private key can issue certificates under it, and a client that still trusts the key accepts
them.

Two rules raise this finding, and both match on the key, never on a name:

| Rule | The certificate | Value shown | `valueType` |
|---|---|---|---|
| 1 | has a listed public key. This catches the certificate eMudhra issued for the key and any cross-signed copy, which carry the same key. | the certificate's SPKI SHA-256 | `spkiSha256` |
| 2 | has a signature that verifies under a listed key: it was signed under a listed intermediate's key, whether or not that intermediate's certificate is in the same file. The signature identifies the key, not who held it. | the certificate's own SHA-256, with the listed key in `issuerSpkiSha256` | `certSha256` |

The SPKI SHA-256 is the SHA-256 of the certificate's DER SubjectPublicKeyInfo, shown as lowercase hex. A
certificate from another eMudhra CA whose key is not listed is not flagged. `cryptoserve scan` reads only the
files in the scanned tree, and a verify sees only the certificates it is given. A result with no finding is
not an all-clear: the check compared only those certificates with the listed keys, and did not check the chain
behind any certificate's issuer.

## Verify

Run from the directory you scanned. `FILE` is the finding's file and `LINE` the line of the certificate's
`-----BEGIN CERTIFICATE-----` header; both are in the finding. The scan prints each command ready to run, and
uses the shorter `openssl x509 -in FILE` form when the certificate is the first PEM block of its file.

Rule 1 prints the finding's `matchedValue`:

```sh
awk 'NR>=LINE' FILE | openssl x509 -noout -pubkey | openssl pkey -pubin -outform DER | openssl dgst -sha256 -binary | od -An -tx1 | tr -d ' \n'
```

Rule 2 prints the finding's `matchedValue`, the certificate's own SHA-256:

```sh
awk 'NR>=LINE' FILE | openssl x509 -outform DER | openssl dgst -sha256 -binary | od -An -tx1 | tr -d ' \n'
```

The commands use only openssl and POSIX tools and read nothing from the network.
Checked under OpenSSL 4.0.3 and LibreSSL 3.3.6, they print the same bytes.

To confirm a rule 2 signature, copy the certificate to its own file (`cert.pem`) and take the listed
certificate for the key in `issuerSpkiSha256` from this repository: `testdata/trust-keys/listed/<certificate
SHA-256>/cert.crt`, for any certificate SHA-256 of that key in the table below. Then:

```sh
openssl verify -no_check_time -partial_chain -trusted listed.pem cert.pem
```

prints `cert.pem: OK`. This needs an openssl that accepts `-partial_chain` and `-no_check_time`: OpenSSL
4.0.3 does; LibreSSL 3.3.6 does not.

## Fix

TLS key:

> Replace the chain with one issued by a CA none of whose keys is listed, and remove this certificate from any bundle or pin set you ship.

Code-signing key:

> Re-sign the artifacts with a certificate from a CA none of whose keys is listed and republish; a verifier that checks revocation can reject signatures under this key.
